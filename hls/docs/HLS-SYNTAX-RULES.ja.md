# LeanからのHLS：IRの構文と変換規則

2026-11-16

本資料は、ESOP論文のRHLによる変換を踏まえ、LeanからRTLへ至るHLSの構成と規則を定める。
計算用IRでは計算とデータの受け渡し方を表し、回路用IRではそれをクロックごとの動作へ具体化する。
規則は現在の変換を説明するための数学的表記である。基本規則と、それらの組合せ・適用方針を区別する。
メモリ変換はESOPの基本規則に基づき、パイプライン化は同じ関係的な判断形式で新しい基本規則を示す。
今後追加する変換は末尾で区別する。

## 1. 全体の流れとstrategy

```text
strategyを指定
        ↓
Leanプログラム（対応する構文・BV32）
        ↓ 解析・意味の接続
┌ 計算用IR ─────────────────────┐
│ 値の計算＋配列更新・分岐・ループ          │
│        ↓ 融合・分割［今後］              │
│ タスク間の配列によるデータ受け渡し        │
│        ↓ バッファ挿入・配列ごとの通信判断 │
│ 局所バッファ＋FIFO／メモリ維持            │
│ ※ ブロック通信・PIPOの選択は［今後］      │
└────────────────────────────┘
        ↓ 制御・記憶操作を具体化
┌ 回路用IR ─────────────────────┐
│ 演算・保持変数・メモリ・FIFO・制御        │
│        ↓ スケジューリング                │
│ クロックごとの演算配置                   │
│        ↓ 保持レジスタの再利用・有限幅化   │
│ 同時更新・条件分岐・ループ制御を持つ回路  │
└────────────────────────────┘
        ↓
    SystemVerilog RTL
```

strategyは変換規則の適用候補を選ぶ方針である。例えば、どの配列をFIFO化するか、どの操作を同じクロックへ置くか、
どの保持変数を同じレジスタへ割り当てるかを選ぶ。候補を選ぶアルゴリズムと、その候補が正しいことの条件は分ける。
strategyを変えても、採用する変換は同じ健全性条件を満たさなければならない。

現在は段階ごとに方針・候補を扱っており、全工程を一括指定するstrategyのインターフェースは今後の課題である。
ユーザーに並列化の正しさをpragmaで宣言させる方式は採らない。関数全体を受ける`hls_program`では反復と処理順をソースから読む。
配列サイズ・公開出力・配置は別途指定する。既存の`hls_certified`では処理本体と外側の反復設定を渡せる。
任意のLean定義からタスクの区切りまで自動推論しているわけではない。

以下では、メモリ変換の正しさを状態関係で、スケジューリングの正しさを操作の依存関係で記述する。

### 1.1 ソースに書く反復と処理順

当面の入口は通常の`def program (s : State) : Option State := do ...`である。
配列はState内に用意し、初期値の書込みは通常の処理としてソースに書く。逐次処理・分岐・入れ子のforを記述順に実行する。
新しい構文をLeanの意味論に追加せず、実行可能な範囲ヘルパーを用いる。

```lean
for i in HybridWord.range start stop stride do
  ...
```

始点・終点・歩幅は生成時に確定する整数で、合意した範囲は非零の歩幅である。範囲の意味は次の通り。

```text
stride > 0 : start + k*stride < stop である k = 0,1,...
stride < 0 : start + k*stride > stop である k = 0,1,...
本体の i   : BV32(start + k*stride)
```

終点への一致は要求しない。反復回数は自然数であり、BV32への折返しで回数は変わらない。実行用ヘルパーでは歩幅0を空範囲としている。
これを既存の`forRange`と添字の式への置換に落とし、制御・回路化でもループを保持する。
一般的な意味保存は`WordLoopFacts.forStatic`、`MemoryCmd.affineLocal_correct`、`Cmd.lower_correct_int`で示す。

`hls_program`の成功結果は`ProgramEntry.compile_correct`で元の関数一回の計算とRTLへ接続する。
固定配列入口は順次処理・静的ループからFIFO最適化用の処理列を自動抽出する。値束縛や分岐をまたぐ分割は行わず、その部分は本体として保つ。[抽出器の範囲と一般証明](AUTOMATIC-STAGES.ja.md)を参照。
この入口と、既存の処理列を渡す入口の最適化範囲を混同しない。

通常入口は`StructuralBody.compileRetained`。補助関数のスカラ実引数を左から順に既存の`letValue`へ保持し、本体では保持値を参照する。State更新後に実引数を再評価しない。通常入口には旧解析器へのフォールバックを置かない。

元構文の生成成功（2026-11-16）：[`OrdinarySource.generates`](../src/IRComparison/Frontend/WordOrdinarySourceInterpretation.lean)が、元のLean構文・型・束縛・独立した環境／固定配列条件から、`compileRetained`成功、生成コードとの対応、Entry構成、`Entry.compile_total`によるRTL生成成功までを示す。保持後・展開後の本体判断、内部型条件、解析成功、生成済みEntryは入口の前提ではない。

入口の判断は`OrdinarySource.Body`／`Function`。Stateの使用条件を`Body.Flow`／`Function.Flow`で付ける。証明用の判断であり、実行IRやユーザー向けDSLを追加しない。既存の`FunctionSyntax.Syntax`は内部の合成判断として再利用する。

```text
補助関数：
  元のラムダ本体の判断 ＋ 元の署名・引数列 ＋ 捕捉Stateの使用条件
  ──────────────────────────────────────────
  元の呼出しの判断

State束縛：
  元の値／処理の判断 ＋ 新しいStateを使う元の後続本体の判断
  ──────────────────────────────────────────
  let s := ... ／ let s ← ... の判断

読出し束縛：
  宣言済み配列の元の読出し ＋ 値変数を使う元の後続本体の判断
  ──────────────────────────────────────────
  let v ← (s.arrays a)[k]? の判断
```

これらの一つの元導出から、`Body.Flow.interpret`／`Function.Flow.interpret`の相互帰納法で内部Syntaxを構成する。補助関数は`FunctionMeaning.ofLambda`で元本体の帰納仮説を一度受け取り、捕捉環境、任意長の引数保持後の本体、Word／BitVec混在の部分適用型を導く。`ArgumentBindings.heldEnvironment`は保持用束縛列を一度たどり、値・State・PUnitの参照位置と型を構成する。State／読出し束縛も同じ帰納法で環境を更新するため、元側と保持後側の本体を二重に利用側で証明しない。

分岐、逐次処理、静的範囲、`List.range n.toNat`の`forIn`／`foldlM`、補助関数の任意の入れ子を扱う。静的境界はIntリテラル・負号・四則演算。反復回数ぶんの展開は行わない。補助関数の引数は既存のState／PUnit／Word／BitVec規約で、Nat反復変数はBV32化してスカラとして使える。

残る入力条件は元定義・標準環境・依存署名の適合、最新Stateの使用、静的なレジスタ番号、固定配列宣言と公開出力の整合性。固定配列入口は互換用の先頭3個のWord引数に依存しない本体を対象とする。生成成功と実行結果の保存、全経路のfuel撤去、最適化予算、回路の実行時間は区別する。[構文ごとの対応表と正確な前提](LEAN-ENTRY.ja.md#現在の最上位保証)を参照。

具体的な入力・保証・残件は[Lean入口](LEAN-ENTRY.ja.md#入口の使い分け)にまとめる。

スカラの局所束縛数に固定上限は設けない。先に束縛した値を、多数の後続束縛や状態更新の後で使うことも対象とする。生成する変数番号の引用は、接続証明と同じ後続数の形を用いる（`WordFrontend.ClosedTerm.bindingIndex`）。これは入力構文やBV32データの表現を変更するものではない。

### 1.2 配列の事前宣言と領域間コピー

配列群を実行前に宣言し、実行中はその領域を使う。新たな配列の確保・拡張・過去の配列版の暗黙保存は許さず、既存領域間のコピーはループ内も許す。
宣言環境を`Γ = {a₁:n₁, …, aₖ:nₖ}`とする。識別子は重複せず、各長さは回路生成時に定まる自然数。番号の連続性や配列0の存在は要求せず、宣言が空の場合や長さ0も許す。

以下はこの方針の構文要約である。`e`は既存のBV32式、`a,b`は宣言済み配列、`n`は静的自然数。

```text
program ::= declarations ; body
body    ::= skip | read x := a[e] | a[e] := e | copy(b,a,n)
          | scalar r := e | let x := e in body | body ; body
          | if e != 0 then body else body
          | for i in range(start,stop,stride) do body

Γ(a) = n    Γ(b) = n
────────────────────── [Copy-Declared]
Γ ⊢ copy(b,a,n)
```

実際のLean記法は`def buffers := #[(0,4),(1,4)]`と、通常のState関数中の`t ← t.copy 1 0 4`。
`hls_fixed_program program using buffers as generated`が本体全体の宣言使用とコピー長を検査し、同じ宣言を記憶配置へ渡す。
ソース関数は既存のLean計算であり、宣言・コピーの意味を公理として追加しない。スカラの局所束縛やStateの逐次受渡しは許す。スカラの`let x := e`は束縛時点の値を保存し、後の状態更新で変わらない。これはループ本体でも同じであり、旧Stateや旧配列全体を保存する機能ではない。

コピーは次の既存IRへ具体化する。`k`は自然数の反復番号を整数として保持し、コピー長をBV32で切り詰めない。

```text
copy(b,a,n)
  ⇒ forRange(n,
       store(b, pure(local(0)), readMem(a,local(0))))
```

両領域の長さがnであるとき、コピー後は`b`の全要素がコピー開始時の`a`と一致し、b以外の配列とスカラ状態は変化しない。
自己コピーも同じ性質を満たす。ループ内で何度実行しても、新たな領域は確保しない。
`FixedMemory.copy_complete`でこの性質を、`FixedMemory.eval_sizes`で本体全体が配列長を保つことを一般証明した。
実装の`State.copy`自体は指定要素数をコピーする実行可能な関数であり、**この入口で両配列の宣言長との一致を要求することで配列全体のコピーになる**。

これは入力の具体化であり、ESOP由来のバッファ挿入・FIFO化の基本規則を置き換えるものではない。
別名で旧Stateを保存して後から読む形は受理せず、必要な内容は明示的なコピー先へ残す。任意のLean配列操作や動的領域管理への対応は含めない。

## 2. 計算用IR

### 2.1 値の計算・読出し・状態更新

計算用IRは、状態に依存しない値の計算、状態を読む計算、状態を更新する処理を区別する。
`a`は配列、`r`はスカラ状態、`k`は束縛位置とする。値のリテラルnは整数、repeatの回数mは自然数である。

```text
v ::= n | index | left | right | local(k) | temp(k)
    | wrap32(v) | natIndex(v) | v+v | v-v | v*v | v div v

E ::= pure(v)
    | readReg(r)
    | readMem(a,v)
    | bind(E,E)
    | select(v,E,E)

M ::= skip
    | letValue(E,M)
    | assign(r,E)
    | store(a,E,E)
    | M ; M
    | if E then M else M
    | repeat(m,M)
    | forRange(E,M)
```

`local(k)`は処理本体のlet束縛、`temp(k)`は読出し計算のbind束縛を参照する。
`index`は外側のカーネル反復の添字、`left/right`は入力スカラ引数を表す。
新しい束縛は値の列の先頭に追加する。

- vは配列・スカラ状態・FIFOを参照しない。
- Eは状態を変更しないが、読出しや束縛参照に失敗することがある。
- Mはスカラ状態と配列を更新する。逐次合成の後半は更新後の状態を使う。
- selectとifは、条件が非0なら前の枝、0なら後の枝だけを評価する。
- repeatは指定回数の反復、forRangeは開始時にEを評価し、`0,…,n.toNat−1` をlocalへ束縛する反復である。

Lean入力のデータはBV32とする。内部の算術表現は整数を使い、BV32の加減乗算では
単項演算 `wrap32(z)=z mod 2³²` を明示する。内部のすべての加算が暗黙にBV32加算になるわけではない。
`natIndex`は整数を自然数へ変換して戻す操作で、負数は0になる。

配列は有限である。配列読出し・更新の範囲外、未定義の束縛参照は失敗する。
未使用の読出しでも失敗を起こし得るので、単に結果を使わないことだけを理由に消去しない。

### 2.2 タスクと反復範囲

```text
Task    = (本体M, 入力配列, start, stride, count, 入出力の情報)
Program = [Task₁,…,Taskₙ] ＋ 配列サイズ ＋ 公開出力
index(j) = start + j * stride       0 ≤ j < count
```

外側の反復は開始値・歩幅・回数を持つ。正逆走査は歩幅で表す。
この反復添字をBV32の入力本体へ渡す箇所では、BV32への変換を行う。
本体内のforRangeとは別の反復構造である。

タスク間のデータ受け渡しは、最初は共有する配列の生成・消費として表す。
タスクへ分割することと、タスクを同時実行することは区別する。融合・分割の自動選択は今後扱う。

### 2.3 バッファ・通信導入後の構文

```text
D ::= Mと同じ形の構文（部分処理もD） | send(E)

L ::= memory(j) | saved(k) | take(d)
Block ::= (反復添字, 読込み操作Lの列, 本体MまたはD)
```

`memory(j)`は入力配列の読出し、`saved(k)`は前回の局所バッファのk番目からのコピー、
`take(d)`はFIFOからd個を捨て、次の1個を受信する操作である。peekは使わない。
読込み列から得た値を、本体が使う局所値として渡す。

本体のsendは1つの出力列へ追加する。どのFIFOに送るかはタスクを包む命令が指定する。
Blockは読込みと本体の組であり、「ブロックストリーム通信」という別の通信方式ではない。

反復ごとにBlockを列挙する形に加え、次の形も用いる。

```text
(start, stride, count, initialLoads, refillLoads, body)
```

この形では初期読込み・補充・本体を一つずつ保持し、コード量を反復回数に比例させずに表す。

## 3. バッファ挿入・FIFO化の基本規則

各規則に対応するLean定理と、実際の変換器・ループ証明・RTL保証への接続は、[規則と実装の対応表](PROOF-MAP.md#rhl-rules-in-the-executable-memory-transformation)からたどれる。

ESOPと同じく、読出し・書込みの置換と、ターゲットだけに行う受信・送信・コピーの挿入を分ける。
窓幅やFIFO化する配列を選ぶアルゴリズムは基本規則には含めない。
既存の変換を維持することより、この基本規則から変換を正当化できることを優先する。

### 3.1 判断と状態関係

```text
{P} M ~ D {Q}          ソースとターゲットの変換
{P} • ~ U {Q}          ソースを進めず、ターゲットにUを挿入
```

PとQは両側の状態についての任意の述語である。特定の窓や添字列テンプレートに限定しない。
有限の計算では、両側が成功してQを満たすか、両側が失敗することを要求する。
挿入判断ではソースのskipが成功するため、Uも必ず成功しなければならない。
事後条件がTrueであっても、空FIFOからの読出しや未定義値のコピーは挿入できない。

メモリ変換で使う基本的な関係を次のように書く。

```text
H_s(a,j)                  ソース配列aのj番目（some v または未定義）
Corr(a,I,Qfifo,s) ≡ |I|=|Qfifo| ∧ ∀k<|I|, H_s(a,I[k])=some Qfifo[k]
AgreeExcept(a,s,t) ≡ 通常のスカラ状態が一致し、a以外の配列が一致
Rel(a,N,I,s,t) ≡ AgreeExcept(a,s,t)
                ∧ size(s.arrays[a])=N ∧ Corr(a,I,t.queue,s)
Hold(a,j,b) ≡ H_s(a,j)=some t.buffer[b]
```

bはターゲットだけの保持値で、通常のスカラ状態の一致対象には含めない。
Iは論理上の添字列であり、データと一緒に回路へ送るタグではない。
同長条件・読出しの非空条件・挿入で使う値の定義性を明示する。

以下のbへの代入は、ターゲットの保持値を扱う規則上の表記である。
混合型IRではlocalの束縛や読込み列で表現でき、コピー時に旧値を読むことを保ったまま具体化する。
新しいソース構文や、実行時に添字から値を探すキャッシュを導入する意味ではない。

### 3.2 読出しの置換：Tr-ReadMem

```text
Hold(a,j,b)
──────────────────────────────── Tr-ReadMem
readMem(a,j) ~ value(b)     （同じ値を返す）
```

ESOPの `x:=a[e] → x:=b` の読出し部分に当たる。
混合型IRでは読出しと、その値の束縛・代入を分けているので、読出しの等価性を先に示し、
bind・letValue・代入へ接続する。式eをjへ置き換えるには、その評価結果がjであることも必要である。

複数の保持値Bについては、次の関係を使ってこの規則を各読出しに適用する。

```text
Buf(a,K,B,s) ≡ |K|=|B| ∧ ∀k<|K|, H_s(a,K[k])=some B[k]
```

例えば既存のlocalがd個あるとき、B[k]は `local(d+k)` で参照する。
この束縛位置の計算は、基本規則をIRの表現へ適用する際の処理である。

### 3.3 書込みの置換：Tr-WriteMem

```text
0 ≤ j < N    j ∉ I    vは評価済み
──────────────────────────────────────────────── Tr-WriteMem
{Rel(a,N,I)} a[j] := v ~ b := v {Rel(a,N,I) ∧ Hold(a,j,b)}
```

この時点ではFIFOへ送らない。ソースの配列だけを更新し、ターゲットでは値を保持する。
`j ∉ I` により、既にFIFOが表しているソース要素の値を上書きしない。
値を求める計算は別に接続し、その計算の失敗も保存する。

### 3.4 挿入規則：Tr-InsRBuf／Tr-InsWBuf／Tr-InsMove

```text
I = j :: J
──────────────────────────────────────────────── Tr-InsRBuf
{Rel(a,N,I)} • ~ b := receive(a) {Rel(a,N,J) ∧ Hold(a,j,b)}

j ∉ I
──────────────────────────────────────────────── Tr-InsWBuf
{Rel(a,N,I) ∧ Hold(a,j,b)} • ~ send(a,b) {Rel(a,N,I++[j])}

──────────────────────────────────────────────── Tr-InsMove
{yが定義済み ∧ [y/b]Q} • ~ b := y {Q}
```

受信は必ずFIFOの先頭を消費する。peekは使わない。
コピーの置換 `[y/b]Q` は、新しいbの値が旧状態のyの値であることを表す。
送信先はこの段階では論理的な列であり、有限容量の検査は後段で行う。

表示した読出し・書込み規則の事後関係は、基本となる状態関係を示したものである。
一般の事後条件については、状態更新による置換と、その含意を証明して組み合わせる。
ESOPの整数・配列意味論をそのまま使うのではなく、有限配列の範囲検査、局所束縛、BV32の演算を保つ。

### 3.5 メモリ維持のための拡張：Tr-InsMemBuf

ESOPの形式化では対象配列をすべてストリームへ変換する。一方、このIRでは配列をメモリのまま残すこともあるため、
メモリから保持値を取り込む挿入規則を追加する。これはESOPの受信規則そのものではなく、同じ挿入判断に対する拡張である。

```text
R ⇒ 両側のa[j]の読出しが同じ定義済みの値vを返す
──────────────────────────────────────────────── Tr-InsMemBuf
{R} • ~ let b := readMem(a,j) {R ∧ Hold(a,j,b)}
```

Rは追加する束縛bを含まない、既存状態間の関係である。ターゲットのメモリ・FIFO・既存状態は変更せず、
読み取った値だけを新しく束縛する。両側の配列が一致し、jが有効な添字なら読出しの前提を満たす。
添字が式の場合は、その評価も含めて読出しの一致・定義性を確認する。
事後条件がTrueでも、範囲外や未定義の読出しを先に挿入してよいことにはならない。

保持した値を後で使うには、挿入後もHoldが成立することを示してTr-ReadMemへ接続する。
現在の窓変換は、対象入力配列を本体が変更しないことと、初期読込み・各補充の全添字が範囲内であることを検証する。
この規則自体は、プログラム全体の配列更新を禁止するものではない。

### 3.6 合成規則

```text
{P} M₁ ~ D₁ {R}    {R} M₂ ~ D₂ {Q}
──────────────────────────────────────── Tr-Seq
{P} M₁;M₂ ~ D₁;D₂ {Q}

{P} • ~ U {R}    {R} M ~ D {Q}
──────────────────────────────────────── Tr-InsertL
{P} M ~ U;D {Q}

{P} M ~ D {R}    {R} • ~ U {Q}
──────────────────────────────────────── Tr-InsertR
{P} M ~ D;U {Q}

P' ⇒ P    {P} M ~ D {Q}    Q ⇒ Q'
──────────────────────────────────────── Tr-Conseq
{P'} M ~ D {Q'}
```

挿入判断にも同じ帰結規則を使う。

```text
Pの下で両側の条件評価が一致する（失敗も含む）
{P ∧ 条件≠0} M₁ ~ D₁ {Q}    {P ∧ 条件=0} M₂ ~ D₂ {Q}
──────────────────────────────────────────────────── Tr-If
{P} if E then M₁ else M₂ ~ if E' then D₁ else D₂ {Q}

任意のkについて {P(k)} M(k) ~ D(k) {P(k+1)}
──────────────────────────────────────────────────── Tr-For
{P(0)} countedLoop(n,M) ~ countedLoop(n,D) {P(n)}
```

Tr-Forは現在のIRの回数指定反復に対する規則であり、ESOPのループ不変条件による合成をこの意味論へ適用する。
反復番号kと実際の添字 `start+k*stride` を区別する。歩幅を1へ制限する条件ではない。
本体内のrepeat・forRangeにも合成規則を用意する。規則が存在することと、現在の自動変換器が
そのループの有用な不変条件を発見できることは別である。

letValueでは両側の読出し結果が一致し、任意の束縛値について本体の変換が成立することを要求する。
そのため、局所束縛を導入したことだけを理由に、任意の場所へ読出しを移動することはできない。

## 4. 基本規則から導く変換と適用方針

当面の適用方針はESOPの読み／書き専用の区別に合わせる。判定単位は既存の処理（stage）であり、
バッファ挿入はその処理が書き換えない入力配列を対象とする。FIFO化では、対象配列について
生成処理は書込み、消費処理は読出しという役割を分ける。同じ処理内で同じ配列を読み書きする場合は、
その配列のバッファ挿入・FIFO化を行わず、メモリ操作を残す。
処理Aが生成し、処理Bが消費する通常の通信は引き続き対象である。

これは入力構文やRHLの一般規則の制限ではなく、最適化の採用方針である。
通常経路の既存のアクセス解析・書込み除外条件を使い、別の役割解析器や型付け機構は追加しない。
同じ配列の消費・補充を扱う専用の不変条件探索は保留し、直近の未完了の拡張は取り除いた。

### 4.1 直接送信

```text
a[j] := v
  ~ b := v                  Tr-WriteMem
  ~ b := v; send(a,b)       Tr-InsWBuf と Tr-InsertR
  ≃ send(a,v)              一時的な束縛を畳み込む
```

直接送信は独立した基本規則ではない。二つの基本規則と挿入の合成から導き、
最後の束縛の除去についても実行結果が一致することを示す。
この形では代入直後に送信する。送信を遅らせるには、間の処理も含めてHoldとRelを保つ証明が必要である。

### 4.2 不要値を捨てて受信する

```text
I[d]=j
Tr-InsRBufをd回適用して不要な値を上書きする
さらにTr-InsRBufを1回適用してjの値を保持する
──────────────────────────────────────────────── 派生変換
memory(j) → take(d)
```

`take(d)` はこの繰返しをまとめた表現である。
供給列 `[0,1,2,3,4]` に対する要求 `[0,2,4]` は `take(0),take(1),take(1)` になる。
供給列の位置とFIFOの値の関係から、各受信が実行可能であることも示す。

一方、供給列 `[0,1,2,3]` から3を受信した後に2を要求しても戻れない。
保持値で解決できなければ、この方法ではFIFO化しない。

### 4.3 窓バッファの構築

窓幅と保持する添字列Kを選ぶことは適用方針である。基本規則は連続した窓を要求しない。
現在の方針では、必要な連続範囲を選び、初期読込み・保持・補充を配置する。

- 既に保持している値はTr-InsMoveでコピーする。
- 新しい値は、メモリ維持ならTr-InsMemBuf、FIFO化するならTr-InsRBufで取り込む。
- 本体の読出しをTr-ReadMemで置き換える。
- Tr-Seq・Tr-If・Tr-Forで全体を組み立てる。

コピー元は旧バッファであり、新しいバッファの構築途中の値ではない。
対象配列の更新で保持値との関係が崩れないこと、先読みによって新たな失敗が発生しないことを確認する。
アクセスの間の穴も読む連続窓では、その穴を含む範囲内条件が必要である。
FIFO化せずメモリを残す場合の先読み挿入は、拡張したTr-InsMemBufに基づく。
count=0では初期読込みをせず、最後の反復後には補充しない。

実行する反復番号をk、窓の添字列をK(k)、保持値をbとすると、関係は
`b = a[K(k)]`（各要素の対応と定義性）である。初期読込みでk=0の関係を作り、
本体の読出しを置換し、次の反復がある場合だけ補充でK(k+1)の関係を作る。
この帰納的な保証から、1つの本体を持つfor全体を導く。反復ごとの本体を生成して検査する方式ではない。

バッファを使うループの保証は、次のRHL判断を合成して作る。

```text
P(k) = 元状態と変換先のデータ状態が一致する
       ∧ 対象の入力配列が変わっていない
       ∧ 保持値が a[K(k)] と対応する

初期読込み：{データ状態の一致} skip ~ 初期読込み {P(0)}
本体      ：{P(k)} 元の本体(k) ~ 読出し置換後の本体(k) {P(k)}
補充      ：{P(k)} skip ~ コピー・読込み {P(k+1)}
```

本体の逐次・分岐は`Relational.seq`／`branch_rule`を使う。
`HybridSymbolicLoop.Plan.body_rule`と`refill_rule`を、共通の派生ループ規則
`Relational.for_with_refill_rule`で合成して`Plan.loop_rule`を導く。
この規則は反復間だけに挿入を行い、最後の反復後には補充しない。
`Plan.initial_rule`を`Relational.insertLeft`で前に接続すると、実際の変換器が使う
`Plan.correct`になる。反復数0は初期読込みも本体も実行しない別のケースである。
従来の`Plan.loop_correct`はこの規則から等式を取り出す互換定理とし、独立した旧帰納証明は残さない。
`bodyStep`／`refillStep`は既存評価器を規則へ渡すための意味上の表記で、新しい実行時IRではない。

バッファ配置のアルゴリズムはFIFO化から独立したまま維持する。
メモリ読込み・コピーの既存補題は、それぞれ`Tr-InsMemBuf`／`Tr-InsMove`を使い、
配列読出しの置換は`Tr-ReadMem`を使う。
その保証を`HybridCompactFIFO.Plan.correct`によるFIFO化、
`HybridSymbolicGlobal.Plan.correct`による処理列の合成へ接続する。
非隣接の生成・消費、A生成→B生成→A消費→B消費も元の順序のまま扱う。解析に適用できない本体は、
`HybridSymbolicLoop.direct`で元の本体とループを残す。入力を拒否したり、全展開してから元に戻したりはしない。

### 4.4 分岐と反復の関係を選ぶ

分岐後のFIFO添字列は、`∃I∈𝓘, Rel(a,N,I)`という事後条件で表せる。
後続の受信コードは、候補となるすべての列で正しくなければならない。
現行のループ保持の窓変換では、本体中の分岐を残し、共通の窓関係で両枝を正当化する。
FIFO連鎖の条件まで示せなければメモリを残す。任意の列集合の不変条件を自動発見する実装ではなく、
隠れた実行時の分岐タグも追加しない。

反復では、初期受信後・各補充後に残る列について不変条件を選び、次の反復へ保存されることを証明する。
現在はアフィンな添字列などの具体的な形を探索するが、そのテンプレートはTr-For自体の制限ではない。

### 4.5 配列ごとの通信判断

プログラム全体でFIFO化する配列の集合Πを固定する。生成・消費について基本規則の適用条件を満たし、
除去対象配列への未変換アクセスが残らず、途中の処理が状態関係を壊さず、公開出力配列を消去しないことを確認する。

バッファ挿入の候補を決めてからFIFO化を判断する。FIFO化できない場合にも、Tr-InsMemBuf等で
正当化できるバッファは残す。この場合はESOPの基本規則にメモリ維持の拡張を加えた変換となる。
既存の変換が基本規則から導けない場合は、その変換を維持するために規則を緩めず、不一致を検討する。

現在の既定実装は、全配列をメモリに保持する証明付き計画から始める。公開出力以外の書込み配列を、ソース中で最初に書かれる順で一つずつ試す。既採用の方針Πへ一配列を追加した**全体計画**を検査し、成功時だけ置き換える。出力数、非干渉、容量・順序などの条件は従来のcompilePolicy／compileStepWithで確認する。局所的に成功した配列を無条件に合成しない。

N配列なら方針の試行は基準計画の後に高々N回で、2^N個の部分集合は構築しない。各試行は処理列全体を再検査するため、コンパイラ全体が線形時間という意味ではない。最大採用数・最適性は保証しない。中間関係には配列ごとの添字列とFIFOを持ち、無関係な処理による破壊を排除する。候補の却下時は直前の正しい計画を保持する。各処理のループは保持する。

純粋な入口は`improve_selected`／`compile_selected`から既存の通信・参照保証へ接続し、`symbolic_compile_total`はメモリ保持の基準計画から生成成功を導く。SMT入口も同じ全体検査を使う。既定30秒の最適化予算が尽きると探索を止め、成功済みの計画を返す。この予算はソース解析のfuelでも回路の実行回数でもない。既に開始した純粋検査・ファイル操作をOSが指定時刻ぴったりに終了させる保証ではない。

外部ソルバーは全体期限と一回15秒の短い方をホスト側で監視し、期限を超えたプロセスグループを停止する。版照会も同じ期限内で行う。要求・応答・stderr・版・終了コード・判断理由を呼出し別のディレクトリへ記録する。キャッシュは使っていない。ログ処理やソルバーが例外を出しても、IO.Refに保持した直前の証明付き計画へ戻る。ソルバーの正しさを新たな仮定にはしない。

期限監視は、直接の子の終了だけでなくstdout/stderr両方のEOFまでを対象とする。`processUntil`は埋込みのPython 3/POSIX監視処理を使い、ソルバーには監視処理自身の外側パイプを継承させない。非ブロッキングreadとwaitpid(WNOHANG)で完了を確認し、期限切れ・待機／読取り例外では親の終了後でも元のプロセスグループへSIGKILLを送る。後始末は最大250msの猶予で回収・reapを試み、回収不能なら読取り側を閉じて不完全な結果として却下する。期限後の無期限wait/getで計画保持への復帰を妨げない。

`process.json`と`version-process.json`には、実際の終了コード（未回収ならnull）、両パイプのEOF、killの成否、後始末の例外、ホスト側の期限到達も残す。`ProcessResult.managementError`が立った結果は採用しない。互換用exitCodeの124は終了コード未回収時の代替値であり、実際のコードはJSONで区別する。

これは厳密な実時間上限ではない。監視処理の起動・OSスケジューリングと、最大250msの後始末分の遅延がある。現在はPython 3とPOSIXプロセスグループが必要。kill権限のエラーや、子孫が別のsessionへ逃れた場合まで強制終了できるとは主張しない。その場合もパイプの回収を無期限に待たず、エラーを記録して既存計画へ戻る。対応する検査は`check-process-supervisor.py`と`check-timeout-retention.py`で実行できる。


現在の部品は、各処理のFIFO入力・出力がそれぞれ高々1つで、各選択配列の生成・消費がそれぞれ1処理で完結する場合を扱う。
条件に合わない入力プログラム自体は禁止せず、該当配列を残す。外部入力をsupplierの添字リストからFIFOにする機能は
旧列挙経路に残り、新経路ではまだメモリから読む。supplierは評価しない。

SMTを使う入口では、Tr-InsMove・Tr-InsRBuf・Tr-Seqとループ関係の初期成立・保存から条件を作り、
各読込み位置の読み捨て数を `d(i)=αi+β` として未知係数を求める。
`先頭添字 + 列の歩幅*d(i) = 必要な添字`、`d(i)≥0`、読込み後の残量が非負、補充後の関係が次の反復へ閉じることを要求する。
アフィンな非負条件は反復範囲の両端で検査する。反復を列挙して制約を作る方式ではない。
これはSATによる候補探索であり、UNSATによる反例不存在の証明ではない。
候補値をLean内で再検査して、既に一般証明した規則の構成子へ渡す。受信変換の健全性はSMTの正しさを仮定しない。
unknown・unsat・不正応答・満たされない規則前提では候補を採用しない。
このアフィンな探索範囲は基本規則自体の制限ではなく、OCaml実装の全VC推論を再現したという意味でもない。

回路への具体化も回数付きループを生成する。`symbolic_pipeline_schedule`から元のLean計算と出力RTLの全体定理へ接続する。
証明で用いる`referenceBlocks`は有限反復の数学的な参照意味論であり、生成器・配置検査・容量検査では構築しない。

### 4.6 filterの例

aは入力、cは公開出力、bは中間配列、N≥3とする。算術はBV32の意味で読む。

```text
元の計算
  producer: for j=0,…,N−1: b[j] := a[j]+1
  consumer: for i=0,…,N−3: c[i] := b[i]+b[i+1]+b[i+2]

バッファ挿入後のconsumer
  B := [b[0],b[1],b[2]]
  for i=0,…,N−3:
    c[i] := B[0]+B[1]+B[2]
    次の反復があれば B := [saved(1),saved(2),memory(i+3)]

bのFIFO化後
  producer: for j=0,…,N−1: send(Qb,a[j]+1)
  consumer:
    B := [take(0),take(0),take(0)] from Qb
    for i=0,…,N−3:
      c[i] := B[0]+B[1]+B[2]
      次の反復があれば B := [saved(1),saved(2),take(0)]
```

最初のFIFO添字列は `[0,…,N−1]`。3個受信すると `[3,…,N−1]` になる。
反復iの本体では `K=[i,i+1,i+2]` とBが対応する。
再利用する値はBから読み、FIFOを巻き戻さない。
この変換自体はproducerとconsumerの同時実行を意味しない。

## 5. 制御・記憶操作の具体化

### 5.1 回路用の式と操作

束縛値を保持変数へ、読込み・状態更新・通信を明示的な操作へ具体化する。
`w`はクロックをまたいで値を保持する変数、`r`は元のスカラ状態を表す。

```text
e ::= fail | n | w | r | a[e]
    | e op e | wrap32(e) | natIndex(e) | select(e,e,e) | checkThen(e,e)
op ::= + | - | * | div | <

A ::= w := e | r := e | a[e] := e
    | snapshot(a,b) | erase(a) | clear(q)
    | send(q,e) | w := receive(q)

C ::= skip | A | C ; C
    | if e then C else C
    | while e do C
```

`checkThen(e₁,e₂)` はe₁の評価成功を確認してe₂を返す。使わない値の読出し失敗を保存する。
`snapshot(a,b)` はbの現在の配列値をaへ複製し、`erase(a)` はaを空配列にする。ゼロ初期化ではない。
`clear(q)` はFIFOを空にする。

loadsの `saved(k)` は保持値のコピー、`memory(j)` はメモリ読出しになる。
`take(d)` はd回の破棄を伴う受信と、その次の値を保持する受信へ具体化する。
回数指定ループはカウンタ、条件判定、更新へ具体化する。ここでのwhileは制御表現であり、Lean入力への新しい構文の追加ではない。

この段階の状態を `σ=(R,H,W,Q)` とする。Rはスカラ、Hは配列、Wは保持変数、QはFIFO。
FIFO容量をκとすると、空FIFOからの受信・満杯FIFOへの送信は失敗する。待機動作にはしていない。

### 5.2 制御の意味

結果は `ok(σ)` または `error`。有限実行を `⟨C,σ⟩ ⇓κ ρ` と書く。
条件が非0なら真の枝、0なら偽の枝を実行する。条件や本体の失敗は全体の失敗になる。

```text
⟨e,σ⟩ ⇓ v    v ≠ 0    ⟨C₁,σ⟩ ⇓κ ρ
──────────────────────────────────────── E-If
⟨if e then C₁ else C₂,σ⟩ ⇓κ ρ

⟨e,σ⟩ ⇓ 0
──────────────────────────────────────── E-Stop
⟨while e do C,σ⟩ ⇓κ ok(σ)

⟨e,σ⟩ ⇓ v    v ≠ 0
⟨C,σ⟩ ⇓κ ok(σ₁)    ⟨while e do C,σ₁⟩ ⇓κ ρ
──────────────────────────────────────────── E-Loop
⟨while e do C,σ⟩ ⇓κ ρ
```

偽の枝の規則も同様。発散はerrorとは区別し、有限実行の導出がない場合として扱う。

## 6. スケジューリング

### 6.1 クロック割当てを付けた表現

```text
B ::= [A₁,…,Aₖ]                  同じクロックの操作
S ::= [B₁,…,Bₘ]                  クロック順の列
T ::= block(S) | T ; T
    | if e then T else T
    | while e do T
```

Bの全操作は、クロック開始時の状態から右辺を評価して更新をまとめて反映する。
Bはリストであり、元の逐次順との関係を確認するための順序を持つ。
1つでも評価・アクセス検査に失敗すると結果はerrorとなる。

### 6.2 読書き依存

R(A)、W(A)を、操作Aが読む／更新する場所の集合とする。
場所はスカラ・保持変数・配列・FIFOで、配列とFIFOは全体を一つの場所として扱う。

| A | R(A) | W(A) |
| --- | --- | --- |
| `w := e` | `reads(e)` | `{w}` |
| `r := e` | `reads(e)` | `{r}` |
| `a[j] := e` | `{a} ∪ reads(j) ∪ reads(e)` | `{a}` |
| `snapshot(a,b)` | `{b}` | `{a}` |
| `erase(a)` | `∅` | `{a}` |
| `clear(q)` | `∅` | `{q}` |
| `send(q,e)` | `{q} ∪ reads(e)` | `{q}` |
| `w := receive(q)` | `{q}` | `{q,w}` |

配列書込みのRにも配列を含めるのは、他の要素の保持と範囲検査が現在の配列に依存するため。
条件式の読出し集合は両枝を含めて安全側に解析するが、実行時に両枝を読むわけではない。
失敗の有無に影響する読出しもRに含める。

### 6.3 順序交換と同時更新

この段階では記憶表現を変えないので、RHLの事前関係を状態の等号、事後関係を成功・失敗を含む結果の等号とする。

```text
W(A)∩R(B)=∅    W(B)∩R(A)=∅    W(A)∩W(B)=∅
──────────────────────────────────────────────── P-Swap
{ = } seq[A,B] ~ seq[B,A] { = }

W(A)∩R(B)=∅    W(A)∩W(B)=∅
──────────────────────────────────────────────── P-SameClock
{ = } seq[A,B] ~ clock[A,B] { = }
```

P-SameClockでは `W(B)∩R(A)=∅` を要求しない。先にAが旧値を読み、後でBが上書きする場合、
同時更新でもAはクロック開始時の値を読むため一致する。

```text
w1 := w0; w0 := 7  ⇒  clock[w1 := w0, w0 := 7]
```

この例は同じクロックにできるが、順序を交換するとw1の値が変わる。
一方、`w0 := a[i]; c[i] := w0` は後半が新しいw0を必要とするので、同じクロックに置けない。

一般の操作列では、すべてのi<jについてP-SameClockの前提を要求する。

```text
∀i<j, W(Aᵢ)∩R(Aⱼ)=∅ ∧ W(Aᵢ)∩W(Aⱼ)=∅
──────────────────────────────────────────────────── P-Bundle
{ = } seq[A₁,…,Aₖ] ~ clock[A₁,…,Aₖ] { = }
```

### 6.4 候補の採用

strategyは操作番号をクロックごとにまとめた候補を作る。例えば `[[0,2],[1]]` はA₀とA₂を同じクロックへ置く候補。
各操作がちょうど1回現れ、並べ替えがP-Swapで正当化でき、各クロックがP-Bundleの条件を満たすことを検査する。

```text
操作の欠落・重複・範囲外番号がない
順序変更がP-Swapで正当化できる
各クロックがP-Bundleの条件を満たす
──────────────────────────────────────────────── P-Schedule
{ = } 元の逐次操作列 ~ 候補のクロック列 { = }
```

候補が不適切なら元の順に1操作ずつ実行する配置へ戻す。
現在は依存制約の下で早いクロックへ置く貪欲な候補を使う。最小IIや最小資源量を保証するものではない。

### 6.5 関係による分岐・ループの合成

メモリ変換と同じく、任意の状態関係Pを使って、逐次・分岐・ループの規則を定める。
こちらは有限実行の保存を示す判断で、ソースの有限実行に対してターゲットの有限実行と事後関係を得る。
失敗も結果として関係付けるが、発散についての双方向同値を主張する判断ではない。

```text
{P} C₁ ~ T₁ {R}    {R} C₂ ~ T₂ {Q}
──────────────────────────────────────── C-Seq
{P} C₁;C₂ ~ T₁;T₂ {Q}

Pの下で両側の条件評価が一致する
{P ∧ e≠0} C₁ ~ T₁ {Q}    {P ∧ e=0} C₂ ~ T₂ {Q}
──────────────────────────────────────── C-If
{P} if e then C₁ else C₂ ~ if e' then T₁ else T₂ {Q}

Pの下で両側の条件評価が一致する
{P ∧ e≠0} C ~ T {P}
──────────────────────────────────────── C-Loop
{P} while e do C ~ while e' do T {P}
```

帰結規則で事前・事後条件を調整できる。現在の構造化スケジューラは、これらをPが状態の等号の場合に適用する。
ループ本体内の進み方は変えられるが、条件判定時には関係を回復する。
動的な反復同士を重ねるには別の適用方法・規則が必要で、C-Loopを用意しただけでは実現しない。

### 6.6 規則を適用する構造変換


`π ⊢ C ⇒ T` を戦略πによる構造変換とする。
Fは分岐・ループを含まない構造を操作列へ平坦化し、できない場合は⊥を返す。
`Sπ(L)` はLに対して候補の検証・必要なら逐次配置への復帰を行ったクロック列。

```text
────────────────────────── T-Skip
π ⊢ skip ⇒ block(Sπ([]))

────────────────────────── T-Step
π ⊢ A ⇒ block(Sπ([A]))

F(C₁;C₂)=L
────────────────────────────────── T-Block
π ⊢ C₁;C₂ ⇒ block(Sπ(L))

F(C₁;C₂)=⊥    π ⊢ C₁ ⇒ T₁    π ⊢ C₂ ⇒ T₂
────────────────────────────────────────────────── T-Seq
π ⊢ C₁;C₂ ⇒ T₁;T₂

π ⊢ C₁ ⇒ T₁    π ⊢ C₂ ⇒ T₂
────────────────────────────────────────────────── T-If
π ⊢ if e then C₁ else C₂ ⇒ if e then T₁ else T₂

π ⊢ C ⇒ T
──────────────────────────────────── T-Loop
π ⊢ while e do C ⇒ while e do T
```

条件式は変えず、選ばれた枝だけを実行する。ループ条件は各反復で再評価する。
本体の更新によって次の条件値が変わる場合も対象となる。
これらの規則は、分岐をまたぐ演算移動や動的ループの反復同士の重ね合わせを行わない。

```text
π ⊢ C ⇒ T    ⟨C,σ⟩ ⇓κ ρ
──────────────────────────── Sound-Structure
⟨T,σ⟩ ⇓κ ρ
```

この保証は任意の入れ子と有限実行に対するもの。任意のwhileが停止するという主張ではない。

### 6.7 ループを展開しない反復の重ね合わせ

既定経路では、メモリ変換の段階から本体とループを保持する。単一処理も、FIFO連鎖に
適用できない処理列も反復を列挙しない。初期読込み・保持・補充の正しさをループ不変条件で
合成してから、同じループ構造を回路制御へ具体化する。後段の静的展開は6.8節の明示選択とする。
まずT-Loopで本体内を配置し、その後、前の反復の末尾と
次の反復の先頭を同じクロックへまとめられるか検査する。
Aは1クロック以上の列、Bは末尾の1クロック、head(A)はAの最初のクロックとする。

```text
Bを正常実行しても条件eの値・定義性は変わらない
B ++ head(A) がP-Bundleの条件を満たす
S = [B ++ head(A)] ; rest(A)
──────────────────────────────────────────────────────── P-Rotate
while e do (A ; B)
  ⇒ if e then (A ; while e do S ; B) else skip
```

Bが条件eの読出し先を書き換えないことを作用の集合で検査する。
同時配置では、前の反復が読む保持値を次の反復が上書きすることは許すが、
前の反復の書込みを次が読む依存や、同じ場所への書込み同士の衝突は許さない。
条件はBの実行前に検査するが、Bが失敗する場合も変換後は失敗する。
終了後の余分なFIFO受信は挿入しない。0回、1回、実行時回数、途中失敗を含む一般規則である。

`Circuit.Pipelining.rotate_correct`がこの規則、`overlapLoops_correct`が変換関数の証明。
既存のClockTreeだけを使い、別の実行意味論や反復数分の操作列を導入しない。
条件を満たさないループは保持する。本体に分岐・内側ループが残る場合は、
内側を再帰的に処理するが、外側の反復同士は重ねない。
準備・排出でコードが増え、短いループでは遅くなることもある。
一般のmodulo scheduling、任意IIの探索、部分展開は今後の課題。

### 6.8 明示的に選択する静的展開

定数と既知の保持値だけで制御が決まる部分は、先に枝を選び、ループを展開できる。
入力配列や実行時パラメータを仮の値に置き換えて制御を決めることはしない。
展開後は反復をまたいでP-Scheduleを適用できる。

`LoopStrategy.rolled`が既定。`.staticExpansion`を指定した場合だけ静的展開を試す。
`fuel`は展開処理の再帰深さの上限で、生成命令数や面積の上限ではない。
既定経路はこのfuelを使わないが、区間解析等には別の探索予算が残る。
未知の制御・展開予算不足ならループ保持経路へ戻る。
構造付き回路の検査が不成立なら、既存の逐次経路を試す。
どの経路でも前段のバッファ・FIFO変換結果は維持する。

## 7. 保持レジスタの再利用と有限幅化

### 7.1 レジスタ再利用

論理上の保持変数wを物理レジスタへ割り当てる写像をμとする。
各クロック境界で、今後使う値の集合Liveについて次の関係を保つ。

```text
LiveRel(μ,Live,σ,τ) ≡ 元のスカラ・配列・FIFO状態が一致
                     ∧ ∀w∈Live, Wσ(w)=Wτ(μ(w))
```

各クロックの書込み先wと、その後も生きている別の保持変数vが衝突しないことを確認する。

```text
各クロックについて、wが書込み先、vが直後にLive、w≠vならμ(w)≠μ(v)
初期状態がLiveRelを満たす
──────────────────────────────────────────────────────── R-Reuse
論理保持変数を使うクロック列 ⇒ μで名前を置換したクロック列
```

同じクロックで最後に読まれる値は、そのクロックの更新時に場所を再利用できる。
右辺が更新前の状態を読むためである。候補が条件を満たさなければ共有せず元の割当を使う。
現在の再利用は静的展開したクロック列が対象で、動的制御を残す経路では保持場所を維持する。
演算器共有を含む一般的な資源割当とは区別する。

### 7.2 有限幅化

各保持変数について値域を求め、符号と幅を決める。
入口の値が範囲内であり、各操作・制御辺を通っても範囲内であることを検証する。
動的制御では位置ごとの区間不変条件を使い、例えば `counter < limit` の真の枝で上界を絞る。

```text
初期状態が範囲内
各制御辺で不変条件が保存される
値域が選んだビット幅で表現可能
──────────────────────────────────────────────────── R-Width
整数で表した回路計算 ⇒ 有限ビット幅で表した回路計算
```

BV32データ演算の丸めは既に式に含まれる。幅の選択によって、整数計算を勝手に別の桁あふれ計算へ変えない。
配列容量、FIFO容量、制御位置の幅、記憶への参照と同時更新の整合性も確認する。
これは採用条件の要約であり、値域だけを確認すれば回路化の全条件が満たされるという意味ではない。

## 8. 制御回路とRTL

### 8.1 グラフの構文

```text
N ::= batch(B,ℓnext)
    | branch(e,ℓyes,ℓno)
    | jump(ℓnext)
    | halt
G ::= (有限ノード配列, FIFO容量表)
```

1ノードが1論理クロックの状態更新を表す。batchは同時更新、branchは条件判定、jumpは次の制御位置への遷移。
whileの本体末尾は条件判定の位置へ戻る。

構造Tを位置bから配置し、成功時にkへ進む配置をL(T,b,k)と書く。

```text
L(block([B₁,…,Bₘ]),b,k)
  = [batch(B₁,b+1),…,batch(Bₘ,b+m),jump(k)]

L(T₁;T₂,b,k)
  = L(T₁,b,b+size(T₁)) ++ L(T₂,b+size(T₁),k)

L(if e then T₁ else T₂,b,k)
  = [branch(e,b+1,b+1+size(T₁))]
    ++ L(T₁,b+1,k) ++ L(T₂,b+1+size(T₁),k)

L(while e do T,b,k)
  = [branch(e,b+1,k)] ++ L(T,b+1,b)
```

sizeは必要なノード数で、blockはクロック数+1、seqは和、ifは両枝の和+1、whileは本体+1。
構造を残す経路では終了ノードを位置0に置き、位置1から開始する。
静的なクロック列だけを直接配置する経路では、先頭クロックから開始して末尾をhaltとする。
分岐・ジャンプもクロックを使うため、操作の束の数だけで全体のクロック数を数えない。

### 8.2 保証する結果

公開する観測を、全スカラと指定された出力配列、および成功・失敗とする。
メモリ変換では配列サイズと必要な入力列の関係を前提として、この観測を保つ。
スケジューリング・レジスタ割当・有限幅化・RTL出力を順に接続し、元の計算から出力RTLまで同じ観測へ到達することを示す。

新しいスケジューリング経路の全体保証は、入力が設定され実行開始状態になった時点からを対象とする。
失敗前の途中配列値、元と同じクロック数、物理遅延やFmaxまでは同一性の対象にしない。

通常のLean入力からの全体定理は、以下の形とする。

```text
compile(f, config) = success(rtl)
InputConditions(config, input)
InitialCorrespondence(input, hardware)
────────────────────────────────────────────────────────
∃ cycles, final.
  runParsedRTL(rtl, cycles, hardware) = final
  ∧ final.done
  ∧ Observe(final) ≈ 終了結果(f, input)
```

入力fは通常のLean関数列と反復設定であり、終了結果はその元の関数を実行した値である。
成功時は全公開出力とエラーなし、失敗時はエラー報告を対応させる。
全公開配列が実際の回路インターフェースに存在することも生成時に検査する。
静的配置・構造化制御・逐次配置の各経路に同じ観測基準を適用し、終了は仮定せず結論とする。
対応入力なら生成自体が必ず成功することと、元と同じクロック数や性能目標を達成することは別の性質である。

## 9. 適用範囲

**入力についての保証**：明示した元の通常Lean構文、型・束縛・環境・固定配列の静的条件から、`OrdinarySource.generates`により`compileRetained`成功、生成コードとの対応、Entry構成、RTL生成成功まで接続した。条件には解析成功、内部検査成功、生成済みEntry、保持後の本体判断を含めない。対象構文の任意の入れ子・組合せを共通の相互帰納法で扱う。詳しい構文対応表と残る前提は[Lean入口](LEAN-ENTRY.ja.md#現在の最上位保証)を参照。

保証は次の二つを区別する。

1. **成功した変換の意味保存**：既存のソース対応・Entry・出力文字列までの正しさ定理を使う。実行時の成功／失敗の観測基準や入力条件は変更していない。
2. **明示した構文・静的条件からの生成成功**：元構文の判断から内部条件を導き、`FixedHLS.Entry.compile_total`へ接続済み。元プログラムの全入力での実行成功、性能目標、物理タイミングの保証を追加する主張ではない。

最適化の条件が示せない場合は、配列のメモリ維持・逐次実行などの保証済み計画を保持する。最適化の不成立や時間予算切れと、旧解析器へのフォールバックは別である。通常入口は`compileRetained`のみで、旧解析器への自動フォールバックはない。


固定配列方式は`State`を明示する入口で実現できた。処理順序はソースの記述順とし、別指定は要求しない。配列確保は実行前の宣言に限り、計算中のコピーは既存領域間で行う。普通の配列への入口変更は必要になれば検討する。詳細は[入口の方針](LEAN-ENTRY.ja.md#入力を書く)を参照。

構文として表現できること、最適化できること、Lean入力からその構文を取り出せることを区別する。

- 制御の構造変換は、分岐・ループの任意の入れ子を扱う。
- 現在の窓変換は外側のカーネル反復を扱う一方、本体内のrepeat/forRangeを含む領域には未対応がある。
- FIFO化は条件を検証できる配列を選ぶ。一般的な多生成・多消費や、一つの処理から複数配列を送る場合には未対応がある。
- 明示した対象構文の入れ子は生成成功証明で扱う。任意のLean構文・再帰・高階関数まで受理する保証ではない。
- SMTは添字列のパラメータ候補の探索に利用する。候補を検査してから変換に接続し、UNSATだけを根拠とする方式にはしていない。


## 10. 配列別判断から回路への接続

通常の入口で実行される経路は次のとおり。

```text
通常のLean定義
  ↓ 既存の入口の接続証明
BV32の本体・カーネル列
  ↓ 窓配置 → プログラム全体で配列別にFIFO／メモリを判断
  ↓ SMTの提案をLeanで再検査（compileWithSMTの場合）
証明を持つ処理列：メモリ／生産／消費／送受信
  ↓ ChannelCommandBridge + ChannelCounted
名前付きFIFOの送受信・私有バッファ・本体・反復
  ↓ ChannelLower.lower
制御を残したSchedule → スケジューリング → 回路 → SystemVerilog
```

配列別判断やSMTの問い合わせを新しく作り直したのではない。
既存の`HybridSymbolicGlobal`が検査した窓配置・通信を、新しい本体で実行する。
処理間のFIFO内容は実際の生産処理が作り、次の処理へ引き継ぐ。
単独の消費例のように、利用者が初期FIFOの内容・添字列の対応を別途与える必要はない。

反復の命令化は、初回に初期読込み、2回目以降に補充を行ってから本体を実行する。
初期窓と補充窓の幅が異なる場合も扱う。補充前にコピー元を束縛し、本体の局所参照を移す。
`ChannelCommandBridge.command_correct`は送信・分岐・束縛・入れ子反復を含む任意の本体について一般証明する。
元の実行で未定義だった局所参照は未定義のまま残る。
`ChannelCounted.command_correct`は任意の回数の反復を扱い、生成時に反復を列挙しない。

外側の処理列は従来どおり、処理開始時の入力配列を専用領域へ保存する。
したがって、途中の配列更新が先読み元を変えてしまう問題を、新しい本体だけで仮定して消してはいない。
また、入力FIFOと出力FIFOが異なること、別の処理用のFIFOが変化しないことを接続時に保証する。
FIFO容量は既存の静的送信上界を使う。容量条件は送信先に必要なものであり、無関係なFIFOへの余分な条件は追加しない。

| 読む箇所 | 保証する内容 |
| --- | --- |
| `Hybrid/ChannelCommandBridge.command_correct` | 既存の本体の出力ストリームを名前付きFIFOにし、局所束縛を移す |
| `Circuit/ChannelCounted.command_correct` | 初期窓・補充・本体・反復と、既存の反復計算の対応 |
| `Circuit/ChannelCountedLower.lower_reference` | 名前付き本体から回路のScheduleまで。有限FIFO容量、失敗、無関係なFIFOの保存を含む |
| `Circuit/CountedBackend.named` | 外側の配列別処理列が必要とする一般的な接続条件 |
| `Circuit.symbolicInstructions_correct_with` | 任意の処理列・複数配列について、処理間の状態とFIFO対応を合成 |
| `Circuit.symbolic_pipeline_schedule_with` | 初期FIFOが空のプログラム全体から有限容量回路への接続 |
| `Pipelining.compileStructured_correct` | 実際の既定の回路生成・出力文字列の実行との対応 |
| `CertifiedHLS.Compiled.correct` | 通常のLean入力から、元の計算の結果／失敗を観測する全体定理 |

`CountedBackend`は新しいIRではなく、実装を差し替えるための証明付きインターフェースである。
既存の直接回路化と新しい名前付き本体経由の回路化が、同じ契約を満たす。
処理列を合成する証明はこの契約で一般化し、二つの経路に同じ長い証明を複製していない。
`ChannelAllocation`はバッファ割当ての共通定義を印字器から分離しただけで、実行動作の追加ではない。

**全体定理の前提は維持している。** 配列サイズ、元の入力条件、有限幅・初期状態の対応を前提に、
生成RTLの有限時間での終了と、宣言した全公開配列・割り当てたスカラの観測一致を結論とする。
変換後の終了性や入力ごとのソース／RTL等価性を新しい前提にはしていない。
元の計算が失敗する場合も全体定理の観測に含まれる。

既定の構造付き経路が新しい本体を使う。明示的に選ぶ静的展開経路と、構造付き回路の検査に失敗した場合の逐次経路は、
既存の直接回路化を使う。いずれも同じ証明済みの窓・通信方針を維持する。

新経路は定義済みフラグと捕捉値を明示するため、旧直接回路化よりサイクル数・保持場所が増える場合がある。
正しさの統合であり、性能改善を主張する変更ではない。物理タイミングは保証しない。

再現は`scripts/certified-hls.lean`、`scripts/rule-vcg.lean`と、それぞれの外部RTL検証スクリプト。
`rule-vcg.lean`は新しい構造付き経路が選ばれたことも検査し、逐次経路へ戻った結果を新経路の成功として数えない。
内部反復の回帰は`scripts/channel-counted.lean`で、異なる窓幅、未定義の局所参照、空反復、他のFIFOの保存も確認する。


## 11. 現在の式表現・入口・外部境界

### BV32の丸め

`HybridIR.Value.wrap32`、`Circuit.Expr.wrap32`、`RTL.Term.wrap32`が同じ`z mod 2³²`を表す。通常のBV32変換は専用演算を使い、範囲は算術式の特定の形によらず`[0,4294967295]`となる。`HybridWord.wrap_correct`、`Circuit.range_correct`、`Circuit.Expr.bitEval_correct`、`RTL.combinational_correct`と出力器の証明へ接続済み。出力では下位32ビットを取得し、ゼロ拡張する。

旧算術式を扱う`wrapped?`と、`HybridAffine`で既存Core.Exprへ渡すための算術式への展開は残る。全経路の式の重複を解消したという主張ではない。

### 組合せ計算の共有

既定の構造付き経路は`ReadCode.bind`を節点と参照として保持する。実行時の束縛環境は節点番号だけを持ち、旧Exprとの対応は証明側の条件である。回路化・範囲解析・参照解析・有限幅化・有効性生成・RTL出力まで共有を使い、値と有効性を一緒に扱う。クロック付きレジスタを追加して共有の代わりにする方式ではない。

`Shared.pipeline_related`、`Shared.generated_text_run`、`Shared.compileStructured_correct`で、計算用IRからソース全体の複数クロック実行へ接続し、通常入口の全体定理が利用する。未使用の不正読出しでも失敗し、未選択分岐の不正読出しは観測しない。

明示的な静的展開と逐次フォールバック等に旧木表現が残ることは、撤去済みの旧Lean解析器とは別である。詳細と計測の読み方は[公開実装の概要](TECHNICAL-NOTE.md)。

### 通常Lean入口

`compileRetained`だけを使う。スカラ・本体・ループ本体は構造再帰、補助関数の実引数は呼出し時に保持する。Source/Syntaxの帰納法もこの方式だけであり、直接代入モードと互換フォールバックは撤去した。

元構文と独立した条件からRTL生成成功までの一般証明は完成済み。型変換の予算の整理や任意のLean構文への拡大とは区別する。[Lean入口の保証](LEAN-ENTRY.ja.md)を参照。

### 外部ポートと初期設定


内部の配列・レジスタIDはNatのまま維持する。32ビットの設定・読出しポートを使う際は、`SystemVerilog.ExternalPorts.Fits`を別途要求する。

- 宣言されたメモリIDとレジスタIDは2^32未満。
- 配列長は2^32以下。最後の要素のアドレスが2^32−1になる配列も表現可能。
- 公開出力は宣言されたメモリに含まれる。

`CertifiedHLS.Compiled.checkExternalPorts`は、実際の生成物についてこの条件を検査して証明を返す。**通常の内部compileはこの追加検査を自動では行わない。** 内部の生成成功定理と、32ビット外部インターフェースの使用条件を区別する。これは任意の大きなIDを外部からアクセス可能にする対応表の実装ではない。

ホスト要求をNatから作る場合は`ExternalPorts.request`／`configuration`を使う。範囲外ならnoneを返し、IDやアドレスを切り詰めない。`request_exact`と`configuration_exact`は成功時の数値の一致を示す。`array_request`と`register_request`は適合条件から要求の存在を導く。

`output_request`は、選択した公開出力が宣言容量内にあり、その要素が存在すれば、その値を要求できることを示す。`emitted_output_request`は、出力器成功・公開メモリの宣言条件の下で、同じ要求が実際の出力文字列のreadTextから値を返すことまで接続する。従来の「表現可能な要求の動作が正しい」より強い、条件付きの全出力要素の取得可能性である。

**任意の合法な初期状態を設定列から構成できるという一般定理は未証明。** `configuration_exact`は要求の座標を表現できることを示すだけであり、設定列全体の到達可能性ではない。既存の準備定理は、与えた設定列が実際に構成した状態から計算が始まることを保証する。

### 今回増やしていない保証

有限FIFOの空受信・満杯送信は失敗であり、バックプレッシャー付き待機ではない。失敗理由や失敗後の状態、同期RAMの遅延、物理タイミング、任意の初期状態の外部設定可能性は保証していない。保証の境界と再現手順は[実装の概要](TECHNICAL-NOTE.md)を参照。
